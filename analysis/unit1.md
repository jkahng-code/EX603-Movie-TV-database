# Unit 1: Modeling Justification and Reflection

## Modeling Justification

For this project I'm modeling a mid-sized streaming platform where users rate movies they've watched, and movies get classified by genre. That gives me the five roles: users, movies, ratings, genres, and movie_genres. Below I'll walk through the main decisions I made and why.

**Primary keys.** For the four main tables I just used a simple integer id (`user_id`, `movie_id`, `rating_id`, `genre_id`) instead of trying to find some "natural" key already in the data. It's simpler and it's what I've seen recommended for most cases. The one exception is `movie_genres`, where the primary key is the combination of `movie_id` and `genre_id` together, since that table only exists to link a movie to a genre and doesn't need its own separate id. One thing I want to call out is that `users` actually has two things that are unique: the `user_id` (the primary key) and `email` (which I made UNIQUE and NOT NULL). I did this on purpose. `user_id` is just how the database keeps track of a user internally and is what other tables use to reference them, but `email` is the real-world rule that no two people should be able to sign up with the same email. They're doing two different jobs even though they're both "unique," so I didn't want to merge them into one column.

**ON DELETE behavior.** For the ON DELETE rules, I tried to be consistent about one idea: normally, deleting something from the platform shouldn't actually delete the row — it should just get marked inactive. Actually deleting a row for good should be rare and something you'd only do on purpose.

That's why both `users` and `movies` have an `is_active` column. If a user closes their account or a movie gets pulled from the catalog, that's just a flag getting flipped, not the row disappearing. This way, if a user deactivates their account, their past ratings still count toward a movie's average, and if a movie gets delisted, people can still see the ratings it already had.

Because of that, the ON DELETE rules only really matter for the rare case where a row actually gets deleted for good. For `ratings.user_id`, I set it to `ON DELETE CASCADE` — if a user's account gets permanently deleted, their ratings should go with it, since you can't even make a rating without an account in the first place, so there's no reason for that rating to still exist once the account is gone. For `ratings.movie_id`, I went with `ON DELETE RESTRICT` instead. Since movies aren't supposed to be permanently deleted under normal use (that's what `is_active` is for), if someone does try to hard-delete a movie, I want the database to stop them until they've dealt with its ratings first, instead of quietly deleting or orphaning all that rating data. For `movie_genres`, both foreign keys use `ON DELETE CASCADE`, since a row in that table doesn't mean anything on its own if either the movie or the genre it's linking is gone.

**Enforced in the schema vs. left to the application.** I made the "one rating per user per movie" rule an actual constraint in the database (`UNIQUE (user_id, movie_id)` on `ratings`) instead of just something the application code checks before saving. I did it this way so the rule is guaranteed no matter what part of the app is writing to the table, instead of depending on someone remembering to check for it in the code. It also means that when a user changes their rating, that's just an `UPDATE` to their existing row, not a new row getting inserted.

## Reflection

One decision a different designer could reasonably have made differently is how I'm handling ratings. Right now a user only gets one rating row per movie, and if they change their mind, it just overwrites the old value. Someone else might've decided to keep every rating a user ever left, each with its own timestamp, so you could actually see how their opinion of a movie changed over time.

I went with just keeping the one current rating because of how I think this platform would actually get used. Most of the queries I imagine running are things like "what's this movie's average rating" or "what genres does this user rate highest," and those only care about someone's current opinion, not their whole history of opinions. If I kept every past rating around, I'd have to add extra logic to every one of those queries just to grab the most recent rating per user per movie before I could even do the math. That's more work for basically every query, just to support a feature (seeing someone's rating history) that isn't actually part of what this platform is supposed to do. On top of that, ratings are probably going to get updated pretty often, so it seemed better to keep that a simple update to one row instead of building out a whole history table full of old ratings nobody's really going to use.
